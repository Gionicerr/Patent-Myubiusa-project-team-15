# Аналитический пайплайн RWB/Russtech

Вход — бизнес-требования и подготовленная техническая конфигурация. Пайплайн обращается к Qwen организаторов, выделяет требования FR-001, задаёт до трёх вопросов, проектирует решение и сохраняет спецификации и документы. Добавлен отдельный явный режим генерации малого серверного проекта с версионированным SQL, сборкой и проверками API/БД; его фактический статус определяется отчётом запуска. Полная генерация приложения, интерфейс, CVE-сканирование и развёртывание пока не реализованы.

## Локальный запуск

Python 3.11 или новее. Для контрактов v2 и отчётов WKT нужны зависимости из `requirements.txt`.

```powershell
python -m venv .venv
.venv/Scripts/Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
# Заполните .env локально; не публикуйте его содержимое.
python server.py
```

Linux: `python3 -m venv .venv`, затем `source .venv/bin/activate`; остальные команды используют `python`. Если в системе нет `ensurepip`, создайте окружение с `python3 -m venv --without-pip .venv` и установите зависимости в него из заранее подготовленных колёс pip/пакетов. Системные Python-пакеты менять не требуется.

Откройте [интерфейс](http://127.0.0.1:8765). Введите требования или подставьте пример и нажмите «Начать анализ». При вопросах ответьте либо явно примите допущения. Единовременно работает один запуск. «Посмотреть готовый пример» загружает заранее подготовленные данные без Qwen; это не подтверждение анализа новых требований.

## Подключение Qwen

| Переменная | Назначение |
|---|---|
| `QWEN_BASE_URL` | Базовый URL либо полный маршрут `/chat/completions` |
| `QWEN_MODEL` | Точное имя модели, без выдуманного значения по умолчанию |
| `QWEN_API_KEY` | Bearer-ключ; пустой допустим, если API не требует авторизации |
| `QWEN_TIMEOUT` | Положительное число секунд HTTP-ожидания, по умолчанию 180 |
| `QWEN_MAX_TOKENS` | Положительный целый предел ответа, по умолчанию 6500 |

Переменные процесса имеют приоритет над `.env`. Настройки адреса и модели подставляются в интерфейс; пустое поле ключа использует серверный ключ. Замена ключа производится через конфигурацию, без правки исходников. Ключ не включается в документы, архивы, browser storage и журналы. `.env` и его варианты исключены из Git и Docker-контекста; пароль ВМ в конфигурацию приложения не входит.

Для организаторов подтверждены `http://10.10.10.10:4000/v1` и `qwen3.8-27b`; доступ к API идёт с ВМ. Порт SSH 10015 не является портом модели. Локальный и серверный `.env` настроены на лимит 16000 и тайм-аут 360 секунд. Для больших спецификаций возможны явные параметры отдельного запуска; успешность такого запроса зависит от квоты API.

```text
python diagnose_qwen.py
python diagnose_qwen.py --report runs/qwen-diagnostic.json
```

Диагностика выполняет один короткий запрос тем же клиентом, ожидает JSON `{"ok":true}`, сохраняет статус, длительность, модель, usage и безопасную категорию ошибки. Код выхода 0 — успех, 1 — ошибка. Отсутствующий usage — `null`, не ноль. Успешная диагностика с ВМ была выполнена: 0,911 с, 66 входных и 44 выходных токена.

Протокол: `POST /chat/completions`, `stream=false`, `temperature=0.2`, `max_tokens`; текст — `choices[0].message.content`. В фактическом ответе шлюза встречаются служебный текст перед `</think>` и экранированный JSON. Общий парсер извлекает финальный JSON и затем строго проверяет его структуру. Дополнительные специфичные параметры модели не используются.

HTTP 401/403/404/429/5xx, сеть, тайм-аут, неверный формат, пустое содержимое и `finish_reason=length` фиксируются как ошибки. Необработанное тело ошибки и Authorization не выводятся. HTTP-перенаправления запрещены. Автоматических сетевых повторов и переключения поставщика нет. Для некорректной структуры допускается одно явное обращение на исправление; каждое обращение учитывается.

## Контракты версии 2

`schemas/design-v2.schema.json` — общий JSON Schema 2020-12. Он не требует парковочных сущностей и используется для новых генераций. Формат содержит:

- сущности, типизированные поля и ограничения, required, PK, FK и индексы;
- дополнительные DTO-схемы, операции API, параметры, requestBody, ответы и коды ошибок;
- роли и области доступа к операциям;
- экраны, отображаемые поля, действия и loading/error/empty/forbidden/ready;
- события, схемы, обязательные поля времени/идентичности и ключи дедупликации;
- сценарии приёмки с FR-ID и operation_id, допущения, ограничения и открытые вопросы.

JSON Schema полей является источником типов и ограничений; `$ref` разрешены только локальные, вида `#/components/schemas/Name`. Имена сущностей становятся схемами компонентов. `openapi.json` версии 3.1.0 детерминированно строится из этого же описания, а не генерируется отдельным несогласованным текстом. Корректность проверяет `openapi-spec-validator`; дополнительно проверяется точное совпадение сохранённого OpenAPI и контракта.

Результаты v1 со свободным текстом продолжают читаться, проверяться и экспортироваться в исходном виде. Типы из старого текста автоматически не выдумываются. Для перехода нужна инженерная ревизия. В Python явный режим совместимости — `Engine(..., design_schema_version="1.0")`; новые генерации по умолчанию требуют `schema_version="2.0"`. Демонстрационный режим сохранён в v1.

Типизированное проектирование по уже проверенному анализу, без повторного анализа требований:

```text
python specify_run.py --requirements examples/parking-stage2-requirements.md --analysis examples/parking-analysis-v2.json --answers runs/stage2/user-clarifications.json --context runs/stage2/input-report.json --parent-run-id a59f1cc9c2e1489ca2b1b6ed2658f889 --output runs/new-specification
```

Файл контекста ограничивается сводкой структуры, статистики и одним примером на источник. Полные `data.zones` модели не передаются. Отчёты разных запусков и родительский ID сохраняются раздельно. Опции `--max-tokens` и `--timeout` изменяют только этот запуск.

Для валидации явно подготовленной инженерной ревизии без вызова модели:

```text
python specify_run.py --requirements examples/parking-stage2-requirements.md --analysis examples/parking-analysis-v2.json --answers runs/stage2/user-clarifications.json --design examples/parking-contracts-reviewed.json --parent-run-id a59f1cc9c2e1489ca2b1b6ed2658f889 --output runs/reviewed-specification
python check_specification.py runs/reviewed-specification --output runs/contract-validation.json
python -m openapi_spec_validator runs/reviewed-specification/openapi.json
```

Режим `--design` помечается `origin=reviewed_contract`, содержит ручное вмешательство и не объявляет подготовленные данные результатом нового вызова Qwen. Проверки документов не являются результатами приёмочного тестирования приложения.

При паузе новый Engine сохраняет `analysis.json` и `pending-report.json` с доступным usage. При ошибке — `failure-report.json`, при отмене — `cancellation-report.json`; метрики уже отправленного запроса сохраняются после его завершения. Пауза не восстанавливается автоматически при перезапуске сервера. Файлы остаются в `runs`, но история интерфейса хранится в памяти процесса. Удаление/перезапуск сервера не считается продолжением старого запуска.

## Парковочные источники и ревизия

Файлы организаторов: `spb.json` — основной; `response.json` — дополнительный город `moscow_partner`. Для программного отчёта:

```text
python report_inputs.py spb.json response.json --regions examples/parking-source-regions.json --output runs/input-report.json
```

Создаются JSON и краткий Markdown. Проверяются все записи, WKT через Shapely/GEOS, типы/отсутствующие поля, вложенные tariff.periods, дубликаты ID, валидность, диапазоны координат и временные метки. Приблизительные регионы в отдельном входном файле — только инженерная проверка порядка координат, не официальные границы.

Подтверждено: spb — 6867 объектов (6563 LINESTRING, 299 MULTILINESTRING, 5 GEOMETRYCOLLECTION); дополнительный источник — 16656 объектов (16326 LINESTRING, 330 POLYGON). Каждая коллекция spb содержит линию и точку. Найдена одна невалидная геометрия `513420` с вырожденным сегментом, а также три повторяющиеся строки геометрии. ID не дублируются; разные объекты не объединяются.

Контракт сохраняет исходные тарифные поля, не интерпретируя неподтверждённые единицы. Предположение EPSG:4326/longitude,latitude согласуется с расположением объектов по городам, но требует подтверждения источника. Линия не задаёт тарифного полигона; коридор — вычисленная область сопоставления. `externalZoneId` трактуется как ID объекта, а не подтверждённый номер тарифной зоны. Невалидная геометрия сохраняется в карантине, не исправляется молча и не участвует в matching.

Исходные шесть FR дополнены до 15 с сохранением FR-001…FR-006. В `runs/stage2/requirements-changes.json` записаны before/after, а в `requirements-coverage.json/.md` — все 13 пунктов полного перечня и критерии. Оригинальный PDF не найден; основание — переданный пользователем перечень и JSON. Полнота спецификации не доказывает полноту будущего приложения.

Порог входа 25 м, выхода 40 м, 3 точки за 15 с, точность до 50 м и неоднозначность менее 5 м — конфигурируемые проектные допущения. Нет совпадения, нет координат и техническая ошибка различаются. Существующая сессия сохраняется; смена объекта и переход по платёжной ссылке не подтверждают оплату. URL официальной оплаты, единицы тарифов, авторитетные границы, модель идентификации и версия серверного PostGIS остаются вопросами. `postgis-jdbc 2.5.0` — Java-библиотека, не версия сервера.

## Фактический статус этапа

Ответы переданы в текущий запуск `a59f1cc9c2e1489ca2b1b6ed2658f889` через обычный `/continue`. Его анализ успешен; проектирование завершилось `finish_reason=length` на 16000 токенов. Итог запуска сохранён как failed, без подмены успехом: 2 обращения, 3617 входных и 23100 выходных токенов суммарно.

Отдельное проектирование v2 по ревизии и один явный повтор после паузы отклонены API с HTTP 429. Их usage неизвестен; ошибки и родительские ID сохраняются раздельно. Бесконтрольные повторы не выполняются. Автоматическое получение полного проекта от Qwen остаётся неподтверждённым до восстановления квоты.

Инженерная ревизия в `examples/parking-contracts-reviewed.json` и `runs/stage2/reviewed-specification/` подготовлена отдельно: 10 сущностей, 21 операция, 5 экранов, 23 сценария. Она проверена как документ; это не результат успешного полного нового запуска модели и не готовое приложение. Происхождение и метрики доступны в отчётах этапа.

## Последовательное проектирование v2 и контрольные точки

Веб-запуски и `specify_run.py` используют общий `app/designing.py`. Планировщик
`design-parts-2` запрашивает архитектуру со стабильным `inventory` и внутренней
`context_map`: связи элементов с FR-ID и уточнениями, включая сквозные вопросы.
Проверяется полнота карты, а не семантическая истинность назначенных моделью связей.
Имена сущностей уже входят в пространство схем; повторять их в `inventory.schemas`
запрещено. Коллизии выводятся с конкретными именами, без автоматического переименования.

Далее последовательно формируются сущности, общие схемы и роли по одной; API и экраны —
пакетами до двух элементов, сценарии — по группе до трёх FR. Последний пакет содержит
допущения, ограничения, вопросы, валидацию и рекомендации безопасности. Состав пакета
проверяется точно: без пропусков, лишних элементов и дублей, с полным покрытием FR
пакета. Итоговый `design.json` сохраняет v2.0; `inventory` и `context_map` в него не входят.
После объединения обязательны полные проверки связей, прав, покрытия и OpenAPI.
На пакет допускаются две попытки за всю историю; исправляется только ошибочный пакет.
Транспортные ошибки, включая 429 и обрезание, останавливают работу без скрытых повторов.
Автоматического изменения размеров пакетов и лимита ответа нет.

Для принятого inventory заметок с пятью FR новый план содержит 8 пакетов вместо 13:
архитектура, сущность, роль, два API, два экрана, две группы сценариев и заключительный
блок. Это расчёт плана, не измерение экономии времени или токенов.

Архитектура получает полный вход. Остальные пакеты получают выбранные по карте FR
целиком с текстом и критериями (без повторения source_quote), относящиеся уточнения,
общие границы/ограничения, права, технический профиль и сводку относящихся элементов.
Не повторяются исходный текст требований, полный analysis со всеми вопросами и
неотносящиеся уточнения. Строки не обрезаются. Машинные ограничения выбранных схем,
ссылочные зависимости, согласованные имена и уже занятые TC-ID сохраняются.
Технический профиль также передаётся на анализ. PWA предусмотрена только при
требовании мобильного интерфейса, для обычного веб-приложения не навязывается.

Пример нового проектирования по проверенному анализу:

```text
python specify_run.py --requirements examples/parking-stage2-requirements.md --analysis examples/parking-analysis-v2.json --answers runs/stage2/user-clarifications.json --context runs/stage2/input-report.json --output runs/design-parts-v2
```

Для одиночных запросов задайте `--api-batch-size 1 --screen-batch-size 1
--scenario-batch-size 1`. Размеры фиксируются при начале этапа; максимумы 2/2/3.
Программный Engine принимает `design_batch_sizes` с ключами api/screens/test_scenarios.

Продолжение новой совместимой контрольной точки — та же команда с теми же входами,
размерами пакетов и `--resume`. В веб-интерфейсе используется прежняя кнопка
«Продолжить проектирование» и `POST /api/runs/<id>/resume-design`.
`design-checkpoint.json` хранит части с хэшами, входы, историю попыток и расход.
Точки `design-parts-1` несовместимы: явная ошибка возникает до записи и новых обращений.
Старые файлы не преобразуются и новый запуск автоматически не создаётся.
Ранее полученные итоговые контракты v1/v2 по-прежнему читаются и проверяются.

Для каждого обращения записываются `context_block_sizes`, `message_sizes`,
`message_content_size`, `parsed_json_size` и `reasoning_prefix_size`: размеры в
символах и UTF-8-байтах, не оценки токенов. `parsed_json_size` измеряет компактную
сериализацию разобранного JSON; префикс рассуждений — до распознанного `</think>`
включительно. Сам текст рассуждений не сохраняется. Отсутствующие размеры — null.
`usage_numeric` содержит только доступные неотрицательные конечные числовые поля
usage (включая вложенные поля; до 64 полей и четырёх уровней), без строковых значений.
Существующие input/output tokens и finish_reason сохраняются, неизвестное не считается нулём.
Неподтверждённых параметров управления рассуждениями нет; общий max_tokens не меняется.

При 429 разрешены только Retry-After и X-RateLimit-Limit/Remaining/Reset-Requests/Tokens
(семь заголовков). Сохраняются числа, длительности сброса или HTTP-даты; неподдержанные
значения отмечаются null. Authorization, остальные заголовки и тело ошибки не сохраняются.
Исторические метрики этими полями задним числом не дополняются.

Сводка источников передаётся через `--context` или `source_summary` веб-API; полные
массивы zones отклоняются, сводка ограничена 32000 символов. Секреты задаются прежним
окружением/локальным `.env` и не входят в контрольные точки. Один каталог обслуживает
один писатель; ожидание ответов этапа анализа автоматически не восстанавливается.
`--design` остаётся отдельным явным режимом инженерной ревизии, а не заменой Qwen.
Генерация и испытания приложения этим этапом не выполняются.

## Первый участок генерации серверного проекта

`generate_server.py` — отдельный явный запуск из проверенных analysis/design v2;
режим получения документов и планировщик design-parts-2 не меняются.
Технические Program.cs, csproj, Dockerfile и Compose формируются шаблоном.
Предметные `src/Domain.cs` и `db/001_init.sql` должны прийти от Qwen: подстановки
демонстрационной реализации при ошибке нет. Npgsql закреплён на версии 10.0.3
([пакет поставщика](https://www.nuget.org/packages/Npgsql/10.0.3)).

Настоящие обращения к API организаторов запускайте только с ВМ, используя
существующий защищённый `.env` пайплайна. Отдельная новая инженерная спецификация
для проверки находится в `examples/notes-server-{analysis,design-v2,provenance}.json`.
Это не завершение старого модельного проектирования заметок и не его замена.
Она явно задаёт владельца из проверенного демо-контекста, ограничения 100/2000,
время UTC, собственные записи и отсутствие интерфейса в данном участке.

```text
python generate_server.py --analysis examples/notes-server-analysis.json --design examples/notes-server-design-v2.json --origin examples/notes-server-provenance.json --output runs/server-demo --verify
```

Если Docker на ВМ доступен только через уже разрешённый sudo, сначала выполните
`sudo -v`, затем добавьте `--sudo-docker`. Группы, системные службы и действующий
аналитический сервер команда не меняет. Каталог output должен быть новым.
Без `--verify` можно отдельно использовать `--build`; без обоих флагов выполняется
только генерация. Готовность приложения не следует из успешной генерации файлов.

Первый генератор поддерживает одну сущность с примитивными ненулевыми полями,
простыми ограничениями и btree-индексами, один серверный UUID, время создания,
владельца из контекста; POST создания и GET массива на одном пути, одна роль own.
Связи, составные ограничения, nullable/сложные схемы и другие формы API отклоняются
до обращения к модели с явной причиной. Имена полей, типы и ограничения берутся
из контракта; генератор не содержит предметных имён заметок.

Каждый ответ модели ограничен одним из двух известных файлов: сначала SQL, затем C#. SQL проверяется до передачи в запрос C#. Абсолютные пути, `..`, symlink,
конфликты имён и попытки изменить сборочные файлы запрещены. Произвольные команды
из JSON не исполняются. Код задаёт argv сборки/Compose без shell; сохраняет коды,
таймеры и журналы. Допускается одна адресная модельная попытка исправления;
429/недоступность API немедленно останавливают обращения. Ошибки среды сборки
не выдаются за дефекты модели или успешную проверку.

Выполнение приложения допускается в отдельном Compose-проекте: непубликуемая БД
postgres:17.9, внутренний network, API на свободном loopback-порту, непривилегированный
пользователь приложения и ограниченные ресурсы. Ключи Qwen и окружение пайплайна
в приложение не передаются. Собственные случайные демо-токены и пароль БД создаются
в защищённом `runtime.env` вне Docker-контекста; файл нельзя включать в архив результатов.
Это демонстрационная идентификация, без регистрации и корпоративной системы входа.

Проверки: реальное создание/чтение, отсутствие доступа без токена, изоляция владельцев,
запрет клиентского owner/time, ограничения полей, перезапуск только API, наличие той же
записи в PostgreSQL и ограничения БД. После проверки контейнеры останавливаются;
при успехе том БД сохраняется. Удаление томов при неуспехе затрагивает только
уникальный Compose-проект этого проверочного запуска, не существующие сервисы.

Файлы результата: `project/`, `attempt-N/generated-files.json`, `commands.json`,
`command-NNN.log`, `generation-report.json`. Происхождение инженерного входа и
модельного предметного кода фиксируется отдельно. `application_verified=true`
ставится только после реально выполненных проверок. При недоступных инструментах,
зависимостях или модели сохраняется соответствующий незавершённый статус.


Раздельный режим `server-files-2` использует два основных обращения (SQL, затем Domain.cs)
и один общий адресный ремонт всего запуска. Успешный файл сохраняется с SHA-256,
происхождением и ссылкой на метрики. Ошибка C# не перегенерирует SQL. Промпты содержат
только модель, ограничения, маршруты и интерфейсы; экранов, сценариев и полного Program.cs нет.
При `--verify` SQL сначала реально применяется к БД и сверяется по столбцам.
Каталог SQL открыт для чтения postgres внутри read-only bind mount; секретный runtime.env
остаётся вне проекта с правами 600, а внешний каталог запуска закрыт.

Для явного продолжения этого же раздельного запуска после устранимой технической ошибки
используйте ту же команду, тот же каталог и `--resume`. Входы, модель и хэши файлов сверяются,
история команд/расхода сохраняется, общий лимит трёх обращений не сбрасывается. Старый флаг
`--repair-truncated` и старые монолитные результаты не преобразуются; для них выдается ошибка.
После 429 или недоступности API обращения останавливаются; продолжение не запускается автоматически.

Функциональный application_verified не означает полного соответствия пакетов конкурсному
окружению. Фактические version() и /etc/os-release PostgreSQL записываются в отчёт; образ
postgres:17.9 дал Debian 13, тогда как заданием указан пакет для Debian 12. Эта часть соответствия
остаётся неподтверждённой. Существующие аналитические этапы и результаты не изменяются.


### Server generation with accepted SQL and operation bodies

Reuse an accepted SQL file without changing the previous run or its call history:

```sh
python generate_server.py --analysis examples/notes-server-analysis.json --design examples/notes-server-design-v2.json --origin examples/notes-server-provenance.json --output runs/handlers-new --accepted-run /path/to/previous/run --accepted-sql-sha256 <verified-sha256> --verify --sudo-docker
```

The source report must mark SQL as Qwen-generated and database-verified; its hash and both input contracts must match. A new output directory is required. SQL bytes are copied unchanged. DTOs, declarations and route wiring come from the typed contract; Qwen supplies only Create and List method bodies. This stage has at most three new calls, including one targeted format/compiler repair. HTTP 429, network errors and truncated answers stop the stage without a model retry. No historical run is resumed or rewritten.

Results: `generation-report.json`, command logs, per-operation accepted responses, `project/provenance.json` and (after actual HTTP checks) `api-evidence.json`. Only successful build and all API/DB checks set `application_verified=true`. PostgreSQL 17.9 on Debian 13 remains a known difference from the specified Debian 12 package.

The generated API binds to VM loopback. For client work use an SSH tunnel: `ssh -p 10015 -L 18880:127.0.0.1:<API_PORT> team15@85.143.113.230`. Configure a local demo token through a protected environment file; obtain its value privately on the VM, never from reports or archives. The API contract is in `project/contract/openapi.json`. Compose stop/start commands must use the same project name and environment file to retain the database volume.
