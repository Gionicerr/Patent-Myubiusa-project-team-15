# Аналитический пайплайн RWB/Russtech

Вход — бизнес-требования и подготовленная техническая конфигурация. Пайплайн обращается к Qwen организаторов, выделяет требования FR-001, задаёт до трёх вопросов, проектирует решение и сохраняет спецификации и документы. Генерация приложения, миграций, сборка, тесты приложения, CVE-сканирование и развёртывание пока не реализованы.

## Локальный запуск

Python 3.11 или новее. Для контрактов v2 и отчётов WKT нужны зависимости из `requirements.txt`.

```powershell
python -m venv .venv
.venv/Scripts/Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
# Заполните .env локально; не публикуйте его содержимое.
python server.py
```

Linux: `python3 -m venv .venv`, затем `source .venv/bin/activate`; остальные команды используют `python`. Если в системе нет `ensurepip`, создайте окружение с `python3 -m venv --without-pip .venv` и установите зависимости в него из заранее подготовленных колёс pip/пакетов. Системные Python-пакеты менять не требуется.

Откройте [интерфейс](http://127.0.0.1:8765). Введите требования или подставьте пример и нажмите «Начать анализ». При вопросах ответьте либо явно примите допущения. Единовременно работает один запуск. «Посмотреть готовый пример» загружает заранее подготовленные данные без Qwen; это не подтверждение анализа новых требований.

## Подключение Qwen

| Переменная | Назначение |
|---|---|
| `QWEN_BASE_URL` | Базовый URL либо полный маршрут `/chat/completions` |
| `QWEN_MODEL` | Точное имя модели, без выдуманного значения по умолчанию |
| `QWEN_API_KEY` | Bearer-ключ; пустой допустим, если API не требует авторизации |
| `QWEN_TIMEOUT` | Положительное число секунд HTTP-ожидания, по умолчанию 180 |
| `QWEN_MAX_TOKENS` | Положительный целый предел ответа, по умолчанию 6500 |

Переменные процесса имеют приоритет над `.env`. Настройки адреса и модели подставляются в интерфейс; пустое поле ключа использует серверный ключ. Замена ключа производится через конфигурацию, без правки исходников. Ключ не включается в документы, архивы, browser storage и журналы. `.env` и его варианты исключены из Git и Docker-контекста; пароль ВМ в конфигурацию приложения не входит.

Для организаторов подтверждены `http://10.10.10.10:4000/v1` и `qwen3.8-27b`; доступ к API идёт с ВМ. Порт SSH 10015 не является портом модели. Локальный и серверный `.env` настроены на лимит 16000 и тайм-аут 360 секунд. Для больших спецификаций возможны явные параметры отдельного запуска; успешность такого запроса зависит от квоты API.

```text
python diagnose_qwen.py
python diagnose_qwen.py --report runs/qwen-diagnostic.json
```

Диагностика выполняет один короткий запрос тем же клиентом, ожидает JSON `{"ok":true}`, сохраняет статус, длительность, модель, usage и безопасную категорию ошибки. Код выхода 0 — успех, 1 — ошибка. Отсутствующий usage — `null`, не ноль. Успешная диагностика с ВМ была выполнена: 0,911 с, 66 входных и 44 выходных токена.

Протокол: `POST /chat/completions`, `stream=false`, `temperature=0.2`, `max_tokens`; текст — `choices[0].message.content`. В фактическом ответе шлюза встречаются служебный текст перед `</think>` и экранированный JSON. Общий парсер извлекает финальный JSON и затем строго проверяет его структуру. Дополнительные специфичные параметры модели не используются.

HTTP 401/403/404/429/5xx, сеть, тайм-аут, неверный формат, пустое содержимое и `finish_reason=length` фиксируются как ошибки. Необработанное тело ошибки и Authorization не выводятся. HTTP-перенаправления запрещены. Автоматических сетевых повторов и переключения поставщика нет. Для некорректной структуры допускается одно явное обращение на исправление; каждое обращение учитывается.

## Контракты версии 2

`schemas/design-v2.schema.json` — общий JSON Schema 2020-12. Он не требует парковочных сущностей и используется для новых генераций. Формат содержит:

- сущности, типизированные поля и ограничения, required, PK, FK и индексы;
- дополнительные DTO-схемы, операции API, параметры, requestBody, ответы и коды ошибок;
- роли и области доступа к операциям;
- экраны, отображаемые поля, действия и loading/error/empty/forbidden/ready;
- события, схемы, обязательные поля времени/идентичности и ключи дедупликации;
- сценарии приёмки с FR-ID и operation_id, допущения, ограничения и открытые вопросы.

JSON Schema полей является источником типов и ограничений; `$ref` разрешены только локальные, вида `#/components/schemas/Name`. Имена сущностей становятся схемами компонентов. `openapi.json` версии 3.1.0 детерминированно строится из этого же описания, а не генерируется отдельным несогласованным текстом. Корректность проверяет `openapi-spec-validator`; дополнительно проверяется точное совпадение сохранённого OpenAPI и контракта.

Результаты v1 со свободным текстом продолжают читаться, проверяться и экспортироваться в исходном виде. Типы из старого текста автоматически не выдумываются. Для перехода нужна инженерная ревизия. В Python явный режим совместимости — `Engine(..., design_schema_version="1.0")`; новые генерации по умолчанию требуют `schema_version="2.0"`. Демонстрационный режим сохранён в v1.

Типизированное проектирование по уже проверенному анализу, без повторного анализа требований:

```text
python specify_run.py --requirements examples/parking-stage2-requirements.md --analysis examples/parking-analysis-v2.json --answers runs/stage2/user-clarifications.json --context runs/stage2/input-report.json --parent-run-id a59f1cc9c2e1489ca2b1b6ed2658f889 --output runs/new-specification
```

Файл контекста ограничивается сводкой структуры, статистики и одним примером на источник. Полные `data.zones` модели не передаются. Отчёты разных запусков и родительский ID сохраняются раздельно. Опции `--max-tokens` и `--timeout` изменяют только этот запуск.

Для валидации явно подготовленной инженерной ревизии без вызова модели:

```text
python specify_run.py --requirements examples/parking-stage2-requirements.md --analysis examples/parking-analysis-v2.json --answers runs/stage2/user-clarifications.json --design examples/parking-contracts-reviewed.json --parent-run-id a59f1cc9c2e1489ca2b1b6ed2658f889 --output runs/reviewed-specification
python check_specification.py runs/reviewed-specification --output runs/contract-validation.json
python -m openapi_spec_validator runs/reviewed-specification/openapi.json
```

Режим `--design` помечается `origin=reviewed_contract`, содержит ручное вмешательство и не объявляет подготовленные данные результатом нового вызова Qwen. Проверки документов не являются результатами приёмочного тестирования приложения.

## Артефакты

| Файл | Назначение |
|---|---|
| `requirements.md`, `analysis.json`, `answers.json` | Вход, анализ и ответы |
| `design.json` | Версионированный проект решения |
| `system-analysis.md` | Назначение, границы, роли, требования, сценарии, компоненты, данные, API, события, ошибки, безопасность и вопросы |
| `openapi.json` | Полная спецификация API v2 |
| `data-model.json`, `permissions.json` | Типизированная модель, связи, индексы и права |
| `screens.json`, `events.json` | Экраны/состояния и события/дедупликация |
| `acceptance-tests.md`, `traceability.csv` | Описания сценариев и связи FR → TC/API; сценарии не исполнены |
| `assumptions-and-questions.md` | Проектные допущения и открытые вопросы |
| `quality-report.json` | Фактически выполненные проверки структуры, их область и метрики |
| `generation-metrics.json`, `specification-run.json` | Метрики и происхождение отдельного проектирования |

При паузе новый Engine сохраняет `analysis.json` и `pending-report.json` с доступным usage. При ошибке — `failure-report.json`, при отмене — `cancellation-report.json`; метрики уже отправленного запроса сохраняются после его завершения. Пауза не восстанавливается автоматически при перезапуске сервера. Файлы остаются в `runs`, но история интерфейса хранится в памяти процесса. Удаление/перезапуск сервера не считается продолжением старого запуска.

## Парковочные источники и ревизия

Файлы организаторов: `spb.json` — основной; `response.json` — дополнительный город `moscow_partner`. Для программного отчёта:

```text
python report_inputs.py spb.json response.json --regions examples/parking-source-regions.json --output runs/input-report.json
```

Создаются JSON и краткий Markdown. Проверяются все записи, WKT через Shapely/GEOS, типы/отсутствующие поля, вложенные tariff.periods, дубликаты ID, валидность, диапазоны координат и временные метки. Приблизительные регионы в отдельном входном файле — только инженерная проверка порядка координат, не официальные границы.

Подтверждено: spb — 6867 объектов (6563 LINESTRING, 299 MULTILINESTRING, 5 GEOMETRYCOLLECTION); дополнительный источник — 16656 объектов (16326 LINESTRING, 330 POLYGON). Каждая коллекция spb содержит линию и точку. Найдена одна невалидная геометрия `513420` с вырожденным сегментом, а также три повторяющиеся строки геометрии. ID не дублируются; разные объекты не объединяются.

Контракт сохраняет исходные тарифные поля, не интерпретируя неподтверждённые единицы. Предположение EPSG:4326/longitude,latitude согласуется с расположением объектов по городам, но требует подтверждения источника. Линия не задаёт тарифного полигона; коридор — вычисленная область сопоставления. `externalZoneId` трактуется как ID объекта, а не подтверждённый номер тарифной зоны. Невалидная геометрия сохраняется в карантине, не исправляется молча и не участвует в matching.

Исходные шесть FR дополнены до 15 с сохранением FR-001…FR-006. В `runs/stage2/requirements-changes.json` записаны before/after, а в `requirements-coverage.json/.md` — все 13 пунктов полного перечня и критерии. Оригинальный PDF не найден; основание — переданный пользователем перечень и JSON. Полнота спецификации не доказывает полноту будущего приложения.

Порог входа 25 м, выхода 40 м, 3 точки за 15 с, точность до 50 м и неоднозначность менее 5 м — конфигурируемые проектные допущения. Нет совпадения, нет координат и техническая ошибка различаются. Существующая сессия сохраняется; смена объекта и переход по платёжной ссылке не подтверждают оплату. URL официальной оплаты, единицы тарифов, авторитетные границы, модель идентификации и версия серверного PostGIS остаются вопросами. `postgis-jdbc 2.5.0` — Java-библиотека, не версия сервера.

## Фактический статус этапа

Ответы переданы в текущий запуск `a59f1cc9c2e1489ca2b1b6ed2658f889` через обычный `/continue`. Его анализ успешен; проектирование завершилось `finish_reason=length` на 16000 токенов. Итог запуска сохранён как failed, без подмены успехом: 2 обращения, 3617 входных и 23100 выходных токенов суммарно.

Отдельное проектирование v2 по ревизии и один явный повтор после паузы отклонены API с HTTP 429. Их usage неизвестен; ошибки и родительские ID сохраняются раздельно. Бесконтрольные повторы не выполняются. Автоматическое получение полного проекта от Qwen остаётся неподтверждённым до восстановления квоты.

Инженерная ревизия в `examples/parking-contracts-reviewed.json` и `runs/stage2/reviewed-specification/` подготовлена отдельно: 10 сущностей, 21 операция, 5 экранов, 23 сценария. Она проверена как документ; это не результат успешного полного нового запуска модели и не готовое приложение. Происхождение и метрики доступны в отчётах этапа.

## Проверки

```text
python -m unittest discover -s tests -v
python check_specification.py runs/stage2/reviewed-specification --coverage runs/stage2/requirements-coverage.json --output runs/stage2/contract-validation.json
```

Тесты используют локальный HTTP-имитатор и отдельный непарковочный контракт. Проверяются типы, ссылки, права, OpenAPI, состояния экранов, события, совместимость, пауза/отмена и защита секретов. Они не подтверждают реальное качество анализа Qwen и не являются испытанием целевого приложения.

Docker: `docker compose up --build`, локальный порт 8765 и том результатов. `.gitlab-ci.yml` отсутствует; CI/CD относится к следующим этапам. Docker-сборку нужно отдельно проверить в окружении с Docker.


Итоговые проверки текущего этапа: **47 тестов локально и 47 на ВМ прошли**, OpenAPI и согласованность всех типизированных артефактов проверены. Полный отчёт — `runs/stage2/stage2-report.json/.md`, архив документов — `runs/stage2/stage2-artifacts.zip`. На ВМ результаты находятся в том же рабочем каталоге, `runs/stage2/`; сервер обновлён и перезапущен после сохранения завершившегося запуска. Секреты не обнаружены в проверенных исходниках, результатах и архиве. Полные исходные JSON остаются в локальном репозитории; модели переданы только сводки и небольшие примеры.


## Регламенты организаторов и подготовка документации

Пять исходных PDF, проверенное текстовое представление, четыре Markdown-шаблона и PlantUML-заготовка находятся в [каталоге регламентов](resources/standards/russtech/README.md). [Таблица соответствия](resources/standards/russtech/mapping.md) отделяет существующие поля от недостающих, а [список будущих задач](resources/standards/russtech/backlog.md) фиксирует применимость и противоречия. Шаблоны не являются поручением реализовать мониторинг, `/health`, `/metrics`, перезапуск и другие будущие возможности.

[Адаптированная документация stage2](docs/stage2/README.md) хранится в репозитории; исходные результаты `runs/stage2/` сохранены. Новое оформление добавляет общие сведения, честный статус TO BE, оглавление и относительные ссылки. FR-ID, JSON Schema и существующие JSON-контракты/OpenAPI не изменены. Согласования, макеты, люди, задачи и измерения не выдумываются; соответствие шаблонам пока частичное.

Локальное повторное оформление и проверка без Qwen и без доступа к ВМ:

```text
python adapt_documentation.py --source runs/stage2/reviewed-specification --output docs/stage2
python check_documentation.py --output runs/documentation-standards/documentation-checks.json
python check_specification.py docs/stage2 --output runs/documentation-standards/contract-validation.json
```

Команда оформления сохраняет машинные файлы побайтно и не допускает совпадения исходного и выходного каталогов. Частично заполненные примеры метода/сервиса и анализ пробелов поддерживаются отдельно; пустые шаблоны явно обозначены. Автоматическая проверка структуры документа не означает корпоративного согласования или проверки работающего приложения.
