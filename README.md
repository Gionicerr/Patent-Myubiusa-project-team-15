# ИИ-аналитик: первый участок пайплайна Russtech

Пайплайн — цепочка шагов, где результат одного шага становится входом следующего.
Эта версия выполняет участок «бизнес-требования → системный анализ → проект решения → план приемочного тестирования».
Это специализированный участок конкурсного задания, а не полный генератор приложений.

## Быстрый старт без модели

Нужен Python 3.11 или новее. Дополнительные библиотеки и установка пакетов не требуются.

1. На Windows дважды нажмите `start.bat`. Либо откройте терминал в этой папке и выполните `python server.py`.
2. Откройте http://127.0.0.1:8765 в браузере.
3. Нажмите «Посмотреть готовый пример».
4. Изучите документы и скачайте ZIP.

**Готовый пример заранее написан. Он не вызывает модель и не анализирует введенный пользователем текст.**
Новая задача анализируется только кнопкой «Начать анализ», после настройки реального API.

## Подключение настоящей Qwen

В разделе «Подключение Qwen» заполните:

- **Адрес API**: базовый адрес из инструкции организаторов, обычно заканчивается `/v1`. Можно вставить полный маршрут `/v1/chat/completions`.
- **Имя модели**: точное значение из инструкции, оно может отличаться от названия в презентации.
- **Ключ**: если API требует авторизацию. Ключ передается только серверу приложения и далее указанному API; в результаты, браузерное хранилище и логи не записывается. Поле очищается после старта. На время запроса ключ хранится в памяти процесса.

Нужен OpenAI-совместимый HTTP API: `POST /chat/completions`, ответ `choices[0].message.content`. Другой протокол потребует доработки `app/provider.py`. Реальный API организаторов пока не проверен: доступ не предоставлен.

Можно заполнить настройки на сервере: скопируйте `.env.example` в `.env`, впишите параметры, перезапустите приложение. Локальный `.env` содержит секрет: не отправляйте его в репозиторий или архив. Ключ из `.env` используется, если поле в браузере пустое. Можно также передавать переменные окружения.

Если Qwen доступна только с VM организаторов, перенесите эту папку на VM и запустите там. Приложение по умолчанию слушает только `127.0.0.1`; доступ через браузер на VM или SSH-перенаправление порта. Не публикуйте его в интернет: здесь нет многопользовательской авторизации. Для Docker адрес `127.0.0.1` в адресе API означает сам контейнер; используйте сетевой адрес Qwen, доступный из контейнера.

## Как работает настоящий запуск

1. Введите 30–20000 символов бизнес-требований.
2. Модель выделяет роли, требования с FR-ID, критерии приемки, риски, допущения и до трех вопросов.
3. Программа проверяет структуру и наличие цитат в исходном тексте. Если ответ некорректен, разрешена одна попытка исправления.
4. Если есть вопросы, запуск останавливается. Ответьте или явно подтвердите продолжение с предложенными допущениями.
5. Модель создает проект системного анализа: компоненты, модель данных, API, пользовательские потоки и сценарии тестирования.
6. Программа проверяет идентификаторы, ссылки на требования и наличие хотя бы одного сценария для каждого FR. При ошибках разрешена одна попытка исправления этого этапа.
7. Документы и метрики сохраняются в `runs/<идентификатор>/`. Их можно скачать по отдельности или ZIP-архивом.

Один активный запуск за раз. На двух этапах всего до четырех обращений к модели, если потребуются исправления. При сетевой ошибке автоматического повторения нет. Отмена локальная: уже отправленный запрос на стороне модели может продолжать выполняться и расходовать токены.

## Что получается

| Файл | Назначение |
|---|---|
| requirements.md | Исходные требования |
| analysis.json | Структурированный разбор требований |
| answers.json | Ответы на уточнения |
| design.json | Структурированный проект решения |
| system-analysis.md | Читаемый документ системного анализа |
| acceptance-tests.md | Описания приемочных сценариев, не результаты запуска тестов |
| traceability.csv | Связи FR → TC и API; открывается в Excel |
| quality-report.json | Реально выполненные проверки структуры и метрики |

Если модель не справилась или API недоступен, формируется `failure-report.json`; полученный ранее анализ также сохраняется.
При перезапуске сервера история в интерфейсе сбрасывается, но файлы в `runs` остаются.

Отчет содержит фактические запросы, повторные попытки, время работы и токены из поля `usage` провайдера. Если API не сообщил usage, расход обозначается как неизвестный, не как ноль. Время обработки исключает ожидание ответов человека; полное время включает его. В учебном примере вызовов модели нет.

## Что проверяется и что требует проверки человеком

Автоматически проверяются формат полей, уникальность FR/TC, наличие цитат во входе, корректность ссылок и покрытие каждого выделенного FR описанием теста.
Это **не доказательство полноты анализа**: модель может пропустить исходное требование или неверно интерпретировать его. Человек должен сопоставить исходный текст с результатом. Найденная цитата подтверждает присутствие текста, а не верность интерпретации.

Код целевого приложения, Android/PWA-приложение, БД, готовый OpenAPI-файл и развертывание целевого приложения эта версия не создает. Тесты целевого приложения и CVE-сканирование не выполняются. Дизайн и меры безопасности являются проектом и рекомендациями. Формального регламента системного анализа организаторов пока нет: после получения следует адаптировать `app/contracts.py` и `app/artifacts.py`.

## Проверка самой программы

В папке проекта:

```text
python -m unittest discover -s tests -v
```

Проверяются ошибки структуры, выдуманные цитаты, потерянные требования, ограничение попыток исправления, пауза на вопросы, метрики, транспорт API, защита ключа от попадания в отчет и скачивание архива. Тестовый API локальный и не является Qwen.

## Docker и GitLab

Если Docker установлен: `docker compose up --build`. Интерфейс доступен на том же локальном порту 8765; результаты хранятся в именованном томе. Не запускайте одновременно Python-версию и Docker на одном порту.

`.gitlab-ci.yml` запускает тесты пайплайна. Нужен Runner с Docker executor и доступом к образу Python; в закрытом контуре образ может потребоваться загрузить заранее. Этот CI не развертывает сгенерированное приложение. Docker и GitLab нужно проверить в окружении команды.

## Что показать экспертам

1. Обозначить специализацию: анализ и документация.
2. Подать новые требования, не только парковочный пример.
3. Показать FR-ID, точные цитаты, вопросы и явно отделенные допущения.
4. Открыть проект решения и связи требований с приемочными сценариями.
5. Показать метрики настоящего запуска Qwen.
6. Объяснить ограничения. Заранее подготовленный пример нельзя выдавать за результат генерации.

## Структура исходников

- `server.py` — локальный сервер и API интерфейса.
- `app/pipeline.py` — последовательность этапов, остановка на вопросы, метрики.
- `app/provider.py` — подключение Qwen.
- `app/contracts.py` — инструкции модели и проверки структуры.
- `app/artifacts.py` — формирование файлов.
- `app/demo.py` — заранее подготовленный учебный пример.
- `static/` — интерфейс на русском языке.
- `tests/` — проверки самой программы.

Python используется для самого пайплайна; в проекте генерируемого впоследствии приложения предлагается конкурсный стек. После первого успешного подключения Qwen следующий этап развития — генерация кода на этом стеке.
