# Краткие правила ведения документации

Источники и оригинальные формулировки: [реестр](README.md#исходные-документы), [текст RULES](extracted/rules.txt), [таблицы RULES](extracted/rules.tables.json). Это структурированная выжимка, не замена исходников. Область текущей работы - оформление и подготовка шаблонов.

## Обязательные описания (M)

1. **DOC-01.** В начале ТЗ: история версий/изменений/оснований, ответственные роли, лист согласования. ФИО, даты согласований и Jira заполняются только по факту; отсутствие сведений отмечается явно (RULES с.1-2).
2. **DOC-02.** Общие сведения: термины, использованные документы, описание изменения, бизнес-цель, границы/ограничения и критерии успеха/приёмки (RULES с.2-3).
3. **DOC-03.** Use Case: ID, название/цель, акторы, предусловия, основной/альтернативные потоки, исключения, постусловия, результат; во второй форме также пусковое событие (RULES с.3-4, включая растровую таблицу).
4. **DOC-04.** Диаграммы последовательности должны иметь редактируемый исходник; указан PlantUML. Скриншоты чужих спецификаций не заменяют диаграмму; при несущественной правке можно сослаться на прежнюю (RULES с.4-5).
5. **DOC-05.** FR нумеруются и трассируются к бизнес-требованиям. Сохраняются ссылки FR - сценарий - API - проверки. В проекте остаётся формат FR-001, а не переименование по примеру FR-1 (RULES с.6).
6. **DOC-06.** AS IS описывает фактически реализованное, TO BE - проектируемое. Изменения ведутся инкрементно, удаление обозначается; проектное поведение не объявляется внедрённым (RULES с.6).
7. **DOC-07.** Связанные сервисы/экраны/методы снабжаются ссылками; если страницы метода нет, допускается ссылка на известный Swagger. Для репозитория используются существующие относительные ссылки (RULES с.6-7).
8. **DOC-08.** FE: элементы, назначение, required, отображение/видимость, доступность disabled/enabled, формат/маска/валидация, обработчик действия и связь с BE; маппинг поля формы в поле API, правила null/пустого/отсутствующего массива/объекта. Учитываются адаптивность, ошибки и завершение сценария (RULES с.6-13).
9. **DOC-09.** При наличии макетов: экраны/изображения/описания, достаточно шагов для понимания процесса. Реальных Figma-ссылок без предоставленных макетов нет; согласование текстовок и макетов с заказчиком не выдумывается (RULES с.6-7,13).
10. **DOC-10.** Интерфейсы взаимодействия: назначение, формат сообщений, защита, частота и синхронизация (RULES с.13).
11. **DOC-11.** БД: отдельно по типам СУБД; поля, типы, обязательность, PK/FK, ограничения; для большого числа таблиц ERD. Новые объекты и удаление отмечаются. Именование требует уточнения из-за противоречия источника (RULES с.14).
12. **DOC-12.** Ресурсное именование путей: RULES с.15 предписывает избегать глаголов в endpoint paths. Существующие action-routes сохраняются по границам текущего задания, а расхождение требует отдельного решения (U-12). API: назначение, аутентификация и права, транспорт/версия, method/path, режим обмена, заголовки, path/query/body отдельно, типы/required/enum/границы/поведение при отсутствии поля; успешные и ошибочные ответы, примеры, алгоритм, обращения к таблицам и внешним системам (RULES с.15-17; API с.1-3).
13. **DOC-13.** Условно применимые части API: при кэшировании - TTL, удаление, refresh/триггеры; при интеграции - источники, типы, маппинг, обязательность и поведение при недоступности. Неприменимость поясняется (RULES с.15-16).
14. **DOC-14.** Интеграции: данные, схемы сообщений, триггеры, частота и особенности; последовательности и зависимости. Не следует объявлять OpenAPI описанием произвольной шины сообщений (RULES с.17).
15. **DOC-15.** НФТ: безопасность, производительность/нагрузка/отклик, масштабируемость, надёжность, сопровождение; резервирование/восстановление, архивирование, доступ, протоколирование, мониторинг, аудит и удалённый доступ. Технические цели отделяются от результатов измерений (RULES с.17-19).
16. **DOC-16.** Описание сервиса: назначение/технологии, ссылки, ресурсы, отказоустойчивость, испытанные пределы, работа/авторизация, Prod/Stage/Test, сборка, деплой, конфигурация/переменные, мониторинг, логирование, сеть и доступы. Отсутствующие окружения так и обозначаются; ресурсные числа не копируются из примеров (SERVICE с.1-3,12).
17. **DOC-17.** В применимом эксплуатационном профиле SERVICE требует описания Prometheus `/metrics`, `/health` со значениями Healthy/Degraded/Unhealthy, критериев/уведомлений, перезапуска, журналов STDOUT/STDERR и доступа к ним. Эти механизмы отложены; требования к отдельному endpoint перезапуска ещё не согласованы (SERVICE с.4,12).
18. **DOC-18.** Если требуется выбор между значимыми архитектурными альтернативами, ADR фиксирует контекст, статус, варианты с плюсами/минусами, решение, последствия и участников. Статус ПРИНЯТО допустим только по факту (ADR с.1).

## Рекомендации (R)

- Краткость и полезность текста; пример ответа BE для FE; несколько показательных примеров запросов/ответов (RULES с.6,15).
- Отдельные дочерние страницы методов и страниц сервисов; в Markdown - каталоги и ссылки (RULES с.6,14).
- Использование общего глоссария БТ; расширение без противоречий. Корпоративный глоссарий не приложен (RULES с.2).
- Диаграмма последовательности для алгоритма API; детальный Flow опционален (RULES с.16).
- Применять шаблон сервиса; полное заполнение требует разработчика, руководителя, DevOps и сетевого администратора (RULES с.13-14; SERVICE).
- Минимизировать бизнес-логику FE; справочники получать от BE. Формулировка о доставке всех текстов с BE содержит оговорку «по возможности» (RULES с.12-13).

## Примеры и справочные материалы (E)

Не являются требованиями парковочного кейса: добавление комментария/смена пароля, регистрация и HTML-элементы, телефоны/имена из демонстраций, схемы чужих БД, API чужих сервисов, .NET7/Linux/10MB/2CPU/5x8/24x7 из примеров, CI с Trivy, конкретные Zabbix Items/Triggers и их пороги, коды 200/401/500 как универсальный полный перечень. Справочные каталоги сохранены в [извлечённом SERVICE](extracted/service.txt) и [таблицах](extracted/service.tables.json), с визуальной оговоркой в [протоколе](extraction-review.md).

## Требуют уточнения (U)

Подробности - [backlog](backlog.md). До подтверждения не переносятся в контракты: противоречивая нумерация, camelCase против `order_id`, схема согласований/корпоративный глоссарий, Swagger для шины, обязательность Zabbix/Elasticsearch/Kibana в контуре хакатона, безопасная модель перезапуска и разделение health/readiness/liveness.

## Адаптация Confluence в репозиторий

| Исходное средство | Markdown |
|---|---|
| Оглавление | Список относительных якорей на заголовки |
| Скрытая история, «Раскрыть» | Обычная таблица; при длинном приложении допустим `<details>` |
| Блок кода/вложение | Fenced code с языком либо существующий относительный файл |
| Цвет/заливка изменений | Текстовые метки ИЗМЕНЕНО/ДОБАВЛЕНО/УДАЛЕНО, версия, FR-ID и ссылка на diff/реестр изменений |
| Статус документа/ADR | Явное текстовое поле; не изображать согласование цветом |
| PlantUML Macro | Исходник `.puml` под версионным контролем; изображение только как производный материал |
| Иерархия страниц | Каталоги документов, индекс и относительные ссылки |
| Недоступная ссылка/редакция | «Не предоставлено»; не реконструировать скрытые значения |
