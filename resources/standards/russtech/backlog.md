# Пробелы, неоднозначности и следующие задачи

Это список подготовки, не поручение реализовать перечисленное сейчас. Обязательность описания не означает наличие работающего механизма.

## Неоднозначности источников

| ID | Источник | Расхождение | Решение текущего этапа / вопрос |
|---|---|---|---|
| U-01 | TZ с.1 против RULES с.1-3 | Дублируются оглавление, номера 2.5.2 и 4.5; различаются 2.4/2.5, 2.5/2.6; в оглавлении пропущена безопасность | Семантика сохранена; шаблон использует последовательность RULES и включает 4.1. Согласовать нормативную нумерацию |
| U-02 | RULES с.14 | camel case сопровождается примером `order_id` | Не переименовывать существующие поля/API. Запросить соглашение именования PostgreSQL |
| U-03 | RULES с.17 | Swagger упомянут для передачи сообщений, далее отдельно шина | OpenAPI оставить для существующего HTTP. Для событий согласовать отдельный формат, не менять контракты автоматически |
| U-04 | RULES с.1,6 | Confluence/Jira, скрытая история и цвет обязательны в корпоративном процессе | Для репозитория - Markdown, таблицы и текстовые метки изменений по запросу пользователя. Уточнить процесс согласований/ролей |
| U-05 | SERVICE с.12 | Unhealthy требует endpoint перезапуска; не определены права, семантика и защита | Не добавлять endpoint в OpenAPI. Позже рассмотреть оркестратор и защищённую административную операцию; согласовать ADR |
| U-06 | SERVICE с.4-12 | Каталог Zabbix и указание конкретных систем логирования не устанавливают применимый профиль хакатона | Согласовать Prometheus/Zabbix/Elasticsearch/Kibana, владельцев, сетевые политики и пороги; ничего не устанавливать |
| U-07 | RULES с.13 | Указаны 100 мс и 1 с как UX ориентиры, но нет нагрузки и цели проекта | Класс R, не объявлять SLO/фактическими измерениями |
| U-08 | API с.2 и RULES с.16 | Пример можно не давать при одних авторизационных данных, но общий совет требует примеры | Отмечать причину отсутствия. Не создавать неисполненные примеры как фактический ответ |
| U-09 | RULES с.12-13 | Тексты с BE «по возможности», далее ограничение бизнес-логики FE | Принцип перенести как рекомендацию; протокол UI-текстов и локализацию проектировать отдельно |
| U-10 | TZ с.1, RULES с.18-19 | 4.2.2 и 4.2.3 названы одинаково, но одна категория про операции, другая про вспомогательные системы | Сохранены обе категории с пояснениями, без слияния |
| U-12 | RULES с.15 и существующий stage2 | Указание избегать глаголов в путях расходится с `/api/sessions/{sessionId}/confirm` и `/api/admin/clock/advance` | Маршруты сохранены побайтно по запросу пользователя. Позже согласовать исключение либо версионированное изменение с совместимостью; сейчас не переименовывать |
| U-11 | RULES с.2 | Корпоративный глоссарий и ссылки на порядок оформления не приложены | Не восстанавливать скрытые ссылки; отметить отсутствие |

## Очерёдность следующего основного этапа

1. Разрешить U-01/U-02/U-03/U-05/U-06 и определить владельцев/применимость.
2. Согласовать необязательный слой метаданных/деталей и совместимость с v1/v2.
3. Сформировать описания из единого источника и проверять их против OpenAPI, схем, FR/UC/TC.
4. После отдельного задания реализовывать приложение, инфраструктуру и фактические эксплуатационные проверки.
