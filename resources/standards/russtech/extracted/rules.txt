2.5 Сценарии использования (UseCase)
Сценарий использования, вариант использования, прецедент использования (англ. use case) — в разработке программного обеспечения и системном
проектировании это описание поведения системы, когда она взаимодействует с кем-то (или чем-то) из внешней среды. Создайте текстовое описание по
шагам или схему на языке uml или используйте готовые Usecase из БТ
UseCase
Основные элементы сценария использования (Use Case):
Идентификатор (ID) — уникальный номер или код для отслеживания сценария использования.
Название (Title) — краткое описание цели взаимодействия пользователя с системой.
Акторы, участники (Actors) — пользователи или системы, которые взаимодействуют с основной системой.
Предусловия (Preconditions) — условия, которые должны быть выполнены перед началом сценария.
Основной поток (Main Flow) — последовательность шагов для достижения цели.
Альтернативные потоки (Alternative Flows) — шаги, которые могут быть выполнены в случае отклонений от основного потока.
Исключения (Exceptions) — возможные ошибки или исключительные ситуации.
Постусловия (Postconditions) — условия, которые должны быть выполнены после завершения сценария.
Ожидаемый результат (Expected Result) — что должно произойти после выполнения всех шагов.

3 Функциональные требования
Каждая функция (пункт) функциональных требований должны быть пронумерованы (например, FR-1, FR-2).
Сделайте трассировку пунктов бизнес-требований и функциональных требований (Трассировка требований - пример)
Frontend (далее FE) и backend (далее BE) могут описываться отдельно в виде спецификаций FE и BE в дочерней структуре страниц родительского ТЗ либо
отдельными нумерованными разделами в общем сквозном описании
Общие правила:
1. Доработки описываются:
a. в формате as is (текущая реализация) для уже реализованного функционала. Например: "Система работает", "Сервис запрашивает",
"Производится проверка" и т.д.
b. в формате to be (будущая реализация) для доработок. После вывода доработки на прод необходимо отредактировать формат to be -
привести к as is.
c. формат "Требуется реализовать" и пр. в том числе используется в постановках в Jira. Без описания в Confluence продуктовая задача
существовать в Jira не может, обязательна ссылка на документацию.
2. В описании Frontend нужно указывать на сервисы backend, которые FE вызывает.
3. Сервисы описываются на страницах профильных пространств. Родительская страница описывает общую информацию, дочерние - методы,
логику работы метода, модель здоровья и т.д.
4. Не пренебрегайте примерами запросов и ответов и другими возможными вариантами пояснения и детализации описания. Любой большой объект
в Confluence (в том числе схему) можно скрыть через плагин "Раскрыть" или "Код". К примеру, ваш сервис вызывает два других сервиса,
обрабатывает их ответ и отдает на FE. Желательно в спецификации BE, как минимум, указать пример ответа на FE или те участки ответов
задействованных сервисов, которые нужны в вашем процессе.
5. Не забывайте при этом, что хорошая статья!=большая статья. Документация не должна быть избыточной, мы пишем не ради процесса, а для
того, чтобы пользователям было понятно и статью было удобно использовать как в процессе разработки, так и в дальнейшей эксплуатации тем,
кто хочет составить понятие о процессе.
6. Если вы ссылаетесь на какой-то другой сервис, экран и пр., то требуется делать гиперссылку на соответствующую статью. Если спецификации
сервиса нет, то в крайнем случае можно сделать ссылку на swagger.
7. Если функциональность не в проде, то во введении можно писать примечания с текстом "В разработке".
В разработке
8. Изменение существующей спецификации, например, модели данных/контракта следует помечать цветом или заливкой для облегчения
визуального восприятия разработчиками границ доработки. После реализации изменения цвет или заливка удаляются. Если что-то в
спецификации удалено, то следует оставить предупреждение об удалении.
9. В таблице История изменений также следует отметить цветом задачу Jira
10. ТЗ одного функционала составляется инкрементами, то есть в каждой новой версии в сквозном описании процесса дополняются
/изменяются существующие разделы

При описании стоит не забыть о таких вещах, как:
Description – короткое описание того, что делает API
Security Schemes – используемый метод аутентификации (часто
встречаемые API Keys, OAuth (2.0), OpenID Connect и HTTP Authentication Schemes – тут так же нужно указать какая именно схема используется.)
Transport security – это может быть обычный открытый HTTP протокол или защищенный HTTPS.
Transport version – HTTP был предложен Тимом Бернерсом-Ли еще в марте 1991-го и за это время вышло несколько обновлений.
Соответственно, важно указать какую из версий вы будете использовать (например HTTP/1.0 ).
Endpoint - не используйте глаголы в endpoint paths, дабы не перегружать его. О том, какое действие с точкой выполняет сервис лучше всего
говорит метод, который используется в HTTP. Лучше использовать существительные, которые представляют собой названия конечной
точки обрабатываемой интерфейсом (например GET /customer/order/{id} лучше, чем GET /customer/getOrder/{id}). Endpoint всегда зависит от
многих факторов и лучше если на проекте определен единый подход к выбору его названия. Если такого нет, то можно этот
момент обсудить с, например, с team lead или architect (в зависимости от вашего проекта и ролевой модели). Посоветуйтесь с разработчиком.
Method – указывает какое действие должен выполнять сервис (например GET /PUT/ DELETE и т.д.). Детальнее об методах HTTP – тут.
Exchange pattern – описание того, как именно должно происходить взаимодействие клиента с сервером (например Synchronous/Asynchronous Re
quest – Response)
Headers – помогают получить дополнительную информацию для управления взаимодействием с API. При этом, важно учесть, что есть
обязательные и необязательные заголовки, в зависимости от выбранного HTTP -Method, а также продумать, какое значение должно приниматься
по умолчанию, если необязательные Headers не указаны.
Request & response parameters – описывая параметры, нужно не забыть указать:
Название параметра;
Тип данных;
Описание;
Наличие справочных значений (enum и его значения);
Обязательность параметра;
Поведение интерфейса, если не передан обязательный или необязательный параметр (для request parameters).
Поведение интерфейса, если не удалось получить/сгенерить обязательный параметр (для response parameters).
Требования к символам, которые необходимо использовать или не использовать.
Если значение числовое, требование к минимальному или максимальному значению.
В зависимости от выбранного типа метода параметры запроса могут передаваться как Path так и в body, поэтому их следует описывать отдельно (для body
чаще всего используют JSON и XML формат).
Request and response examples – в идеале, сделать несколько примеров на разные кейсы, при этом самое главное – увидеть полную структуру.
Errors – условно можно поделить на:
полученные от системы источника данных (например, API не смогло подключиться к источнику из-за того, что он недоступен
/источник вернул ошибку обработки данных);
ошибки API (любая логическая ошибка и т.п.);
ошибки подключения к серверу (когда запрос еще даже не дошел до API и где-то потерялся API Manager);
Caching – если вы планируете реализовать кеширование, необходимо указать:
максимальное время актуальности данных в кеш;
логику удаления записи из кеша;
возможность принудительного обновления данных, которые хранятся в кеше;
триггер для актуализации данных в хранилище.
